# i915 Meteor Lake GuC TLB-invalidation timeout → desktop stall — Research Report

**Date:** 2026-08-29
**Upstream:** [drm/i915 issue #14469](https://gitlab.freedesktop.org/drm/i915/kernel/-/issues/14469) (open since 2025-06-13, 49 participants)
**Status on this machine:** UNFIXED. The fix exists but is not obtainable here yet.

## Executive Summary

Random 5-15s desktop stalls. The GPU microcontroller (GuC) stops answering TLB
invalidation requests; the i915 display flip worker blocks; anything waiting on
the display pipeline stops.

**Root cause (Intel, in-thread): the GuC dies while waking the hardware from
RC6.** The fix is in **PCODE**, which ships inside **Intel CSME firmware**,
which ships inside **OEM BIOS**. It is not a driver bug — the same failure
occurs on both `i915` and `xe`.

**Required: CSME >= 18.1.18.2644.** This machine is on **18.0.5.2141**, the
factory original. BIOS N48ET34W (1.21, 2026-05-11) did **not** bundle it, and
`fwupd` offers no ME update even with `lvfs-testing` enabled.

Check it:

```bash
cat /sys/class/mei/mei0/fw_ver     # want >= 18.1.18.2644
```

## Why this report is high-confidence

A reporter in that thread — Russell Teague (@mtnbikenc) — has the **same laptop
model**, ThinkPad P1 Gen 7 (type 21KV/21KW), and did the elimination work over
five months. VERIFIED from his posts:

| Attempted | Result |
|---|---|
| Lenovo BIOS 1.19 | ❌ no change |
| CSME 18.0.15.2515 | ❌ no change (insufficient version) |
| **CSME 18.1.18.2724** | ✅ hangs stopped — 26+ days clean, his longest gap ever |
| `i915.enable_guc=0` / `=2` | ❌ **system will not boot** on MTL — GuC is mandatory |
| `i915.enable_dc=0` | ❌ no change — *this image already sets it* |
| `i915.enable_psr=0` | ❌ no change — *this image already sets it* |
| `xe` driver | ❌ **worse** — silent hard lockups and failed resumes |
| kernel 6.17.8 → 6.18.13 | ❌ persists across all |

Two other MTL reporters improved (~6 months and ~2 months clean) but **both are
confounded** — one changed `intel_pstate=passive` and disabled HyperThreading
at the same time; the other says outright "I don't know" what fixed it.

**Do not treat a kernel bump as a fix for this.** UNVERIFIED whether 7.x helps
on MTL; the positive reports are not clean A/Bs, and Intel's stated mechanism is
firmware, not driver.

## Symptom on THIS machine — the mild variant

VERIFIED 2026-08-29, captured by `bazzite-tower-stall-detect`:

```
===== STALL 8.12s at 2026-08-29T08:19:54 =====
D  kworker/20:1+usb_hub_wq
D  kworker/u92:3+i915_flip        <-- display flip worker BLOCKED

08:19:45  thunderbolt 0000:00:0d.2: 0: timeout reading config space 1 from 0xaf
08:19:54  i915: *ERROR* GT0: GUC: TLB invalidation response timed out seqno 4122630
08:19:54  i2c_designware: i2c_dw_handle_tx_abort: lost arbitration
```

We get the TLB timeout but **not** the escalation the thread's hard-freeze cases
show. No `GPU HANG: ecode 12:0:00000000`, no `Resetting chip for stopped
heartbeat`, and `/sys/class/drm/card1/error` stays empty. Their cases show
11-20 consecutive TLB timeouts over ~25s before the hang; we get one and an ~8s
stall that recovers.

The original reporter described exactly this earlier stage: *"similar
stutters... GPU was able to recover itself in 3-5 seconds."* Same bug, caught
before it escalates. **It can get considerably worse than what we see.**

RC6 residency here is ~47% of uptime, so exposure is high.

## Why no kernel watchdog reports it

VERIFIED by inspection and by the absence of any kernel message at stall time:

- the **soft-lockup watchdog** only fires on a CPU *spinning* in kernel mode
- **`hung_task`** only fires after `hung_task_timeout_secs` (default 120s)

A 5-15s stall caused by a *blocked* worker trips neither, at any threshold
setting. This is why the stutters went unexplained for months. It is also why
`bazzite-tower-stall-detect` exists — its D-state snapshot is the only thing
that identifies the subsystem.

## Thunderbolt correlation — NOT ESTABLISHED

Thunderbolt config-space timeouts appear near two of the events (17:15:18-19 on
2026-08-28, 08:19:45 on 2026-08-29). **n=1 for actual co-occurrence**, with a
counter-example (17:15 had Thunderbolt and no GuC timeout). Recorded as a lead
only. Do not report this upstream without more samples — `ujust freeze-report`
is there to accumulate them.

Note also: a thread reporter with a similar "stall, no GPU HANG" presentation was
told by Intel that his was *"a completely different issue"* and asked to file
separately. His had no TLB timeout; ours does, so we sit closer to the main bug —
but the boundary is not crisp.

## Actionable paths, ranked

1. **Obtain CSME >= 18.1.18.2644.** The actual fix. Lenovo publishes it under the
   **Chipset** category, not BIOS (other users cite package codes `NWME22WW`,
   `n48rg02w`, typically Windows `.exe`). One reporter received 18.1.18.2724 via
   fwupd/LVFS in April 2026, so an LVFS path exists — it is simply not offered
   for machine type 21KV as of this writing. Re-check periodically.
2. **Disable hardware video acceleration in browsers.** Zero risk, available now.
   Every thread reporter who identified a trigger named browser video playback;
   two independently confirmed this stabilised their system. Costs smoothness
   and CPU.
3. **Stay off the `performance` platform profile.** One reporter: crashes
   "multiple times a day" on performance, "rarely if ever" on power saver. This
   image defaults to `balanced` — leave it.
4. **Patch the kernel to restore `i915.enable_rc6`.** Intel's Daniele Ceraolo
   Spurio posted the patch in-thread; two users confirmed it works. Costs real
   battery life and means carrying a kernel patch on a bootc image. Reserve.
5. **Render on the NVIDIA dGPU.** Would sidestep the i915 GuC entirely. Untested
   here; the hybrid stack changes with the `bazzite-nvidia-open` move, so
   revisit after that lands.

## What NOT to do

- **Do not switch to `xe`.** VERIFIED worse on this exact laptop model: silent
  hard lockups and failed resumes instead of a recoverable stall.
- **Do not set `i915.enable_guc=0` or `=2`.** VERIFIED: the machine will not boot.
- **Do not add more `i915.enable_*` kargs hoping to hit it.** `enable_dc=0` and
  `enable_psr=0` are already set here and are documented upstream as ineffective
  against this bug. They are present for the *cx0 resume* regression
  (`i915-mtl-resume-2026-06-20.md`), a different problem.
